# YAML-конфигурация и сбор

## Контракт YAML

Конфигурация декларативна и описывает один источник. В БД сохраняется только YAML, успешно прошедший dry run. Сервер выдаёт краткоживущий `test_token`, привязанный к хешу YAML и тестовому URL; сохранение или обновление источника требует этот токен. Импорт YAML также должен пройти dry run.

Полный шаблон находится в [examples/source.example.yaml](examples/source.example.yaml). Его поля и допустимые значения образуют контракт конфигурации; новые поля нельзя добавлять без изменения парсера и документации.

`scroll_or_button` скроллит страницу и, когда доступна кнопка, нажимает её. Если пагинация не требуется, блок отсутствует: типа `none` нет. Динамика описывается ограниченными параметрами ожидания и остановки, а не произвольным JavaScript. Перед запуском валидируются обязательные поля, URL, допустимые значения, CSS-селекторы и лимиты.

Поисковую фразу пользователь вводит при ручном запуске: в поле запуска
источника или через CLI `-search`. Если задан `search_url_template`, все
`{query}` заменяются URL-кодированным значением; иначе `search_on_ui` вводит
фразу в `input_selector` и отправляет её кнопкой либо Enter. Пустая фраза не
изменяет стартовый URL и не выполняет UI-поиск.

Для подготовки нового конфига по HTML используется готовый [промпт для LLM](examples/llm-config-prompt.md). Полученный YAML обязательно проверяется через dry run: ответ модели — гипотеза, а не подтверждение работоспособности.

## Детальная страница вакансии

Список вакансий часто содержит только название и ссылку. Необязательный блок `detail_page` включает последовательный обход ссылок после сбора списка и дополняет существующую вакансию. Поля, найденные на детальной странице, заменяют одноимённые непустые поля карточки; если страница не загрузилась или селектор ничего не вернул, остаётся значение из списка.

```yaml
detail_page:
  wait_for_selector: "main"
  timeout_seconds: 30
  selectors:
    title: "h1"
    company: ".vacancy-company"
    salary: ".vacancy-salary"
    description: ".vacancy-description"
```

Для `detail_page` обязательны `wait_for_selector`, `timeout_seconds` и как минимум один селектор поля. На текущем этапе ссылки обходятся последовательно, чтобы не создавать лишнюю нагрузку на сайт. Ошибка одной детальной страницы записывается в результате запуска и не отменяет уже извлечённый список; в будущей БД такой запуск будет иметь статус `partial`.

## Идентичность вакансии

Без блока `identity` нормализованный URL является идентичностью вакансии. Для
сайта, который выдаёт новый URL одной и той же вакансии на каждом запуске,
задайте `identity.fallback_fields`. Допустимы `title`, `company`, `salary` и
`description`; непустой список всегда заменяет URL как ключ сопоставления.
Выбирайте только достаточно устойчивые поля: изменение значения либо состава
списка намеренно создаёт новую вакансию.

## Как подготовить материалы для LLM

Чтобы агент составил конфиг без догадок, передайте ему [шаблон промпта](examples/llm-config-prompt.md), содержимое [YAML-шаблона](examples/source.example.yaml) и материалы ниже.

1. **Страница списка:** URL и HTML после отрисовки JavaScript. Нужен фрагмент с контейнером списка, двумя-тремя карточками, поиском и пагинацией, если они есть.
2. **Детальные страницы:** если ссылка карточки ведёт на отдельную вакансию, передайте URL и HTML после отрисовки хотя бы одной такой страницы. Лучше приложить две страницы с разным наполнением: например, с зарплатой и без неё.
3. **Поведение страницы:** укажите, что происходит после скролла, клика «Показать ещё», ввода запроса или перехода по ссылке. Если это неизвестно, так и напишите — агент должен спросить, а не угадывать.
4. **Цель сбора:** какие поля важны (`title`, `company`, `salary`, `description`) и нужно ли выполнять поиск. Не передавайте cookie, токены, персональные данные или HTML авторизованной сессии.

HTML нужно брать из уже отрисованной вкладки браузера, а не только из ответа `curl`, если сайт использует JavaScript. Подойдут «Inspect element» → Copy → Copy outerHTML для списка/`main`, сохранённый DOM из DevTools либо результат диагностического режима парсера. При отсутствии HTML детальной страницы агент должен вернуть вопросы и не добавлять `detail_page` наугад.

## Алгоритм запуска

1. Создать `scraping_runs` со статусом `running`, захватить блокировку источника и создать контекст с таймаутом.
2. Открыть изолированный Chromium, загрузить URL, дождаться `wait_for_selector`; при необходимости выполнить UI-поиск.
3. Выполнять пагинацию до стоп-условия, лимита, таймаута либо отмены и записывать диагностику.
4. Получить итоговый DOM, извлечь карточки goquery, очистить текст и нормализовать ссылки.
5. В одной транзакции создать/обновить вакансии, записать историю отслеживаемых полей и состав запуска.
6. Архивировать отсутствующие вакансии только при `status=success` и `completion_status=complete`.
7. Записать итоговые счётчики и состояние источника, снять блокировку.

При ошибке, блокировке, неполной выдаче или неопределённом завершении активные вакансии не архивируются. Глобальная конфигурация приложения задаёт лимит браузеров, таймауты, задержки и максимум карточек за запуск.
