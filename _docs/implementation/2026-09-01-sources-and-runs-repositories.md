# Репозитории источников и запусков

**Дата:** 2026-09-01  
**Статус:** выполнено  
**Этап ТЗ:** [этап 0 — фундамент](../05-implementation-plan.md#этап-0--фундамент)

## Проблема и цель

SQLite-схема уже существует, но прикладной код не может безопасно сохранять
источники и фиксировать жизненный цикл запуска без прямого SQL. Это мешает
подключить скрапер к постоянному хранилищу и позднее предоставить одинаковое
поведение CLI и HTTP API.

Цель инкремента — дать приложению минимальный типизированный доступ к
`sources` и `scraping_runs` с проверяемыми инвариантами статусов.

## Границы

Входит:

* модели источника и запуска, соответствующие начальной схеме;
* создание, получение и обновление источника по идентификатору;
* создание запуска в состоянии `running` и его завершение;
* получение последнего запуска источника;
* тесты CRUD, уникальности slug и корректных переходов статуса.

Не входит:

* HTTP API, YAML dry run, расписания и блокировки параллельных запусков;
* сохранение вакансий, истории, состава запуска и архивирование;
* генерация UUID: идентификаторы передаёт вызывающий сервис следующего слоя.

## Решение

Методы будут частью `storage.Store` и использовать контекст вызывающего кода.
Значения даты передаются и возвращаются как `time.Time`, а в SQLite сохраняются
UTC-строкой ISO 8601. Это устраняет зависимость от локальной зоны процесса.

Создание запуска обновит состояние источника на `running` в той же транзакции.
Успешное или ошибочное завершение запуска запишет итоговые счётчики и обновит
у источника `status`, `last_run_at` и `last_error`. Запуск можно завершить
только из `running`; повторное завершение вернёт ошибку и не изменит данные.

## Проверка и результат

Тесты выполняются на временном SQLite-файле:

1. сохранение, чтение и обновление источника, включая UTC-времена;
2. отклонение повторяющегося `slug`;
3. создание запуска переводит источник в `running`;
4. успешное завершение обновляет счётчики и состояние источника;
5. повторное завершение того же запуска возвращает ошибку перехода;
6. получение последнего запуска возвращает наиболее новый запуск источника;
7. запрос отсутствующего источника возвращает отдельную ошибку «не найдено».

Все перечисленные сценарии пройдены. Репозитории возвращают `ErrNotFound` для
отсутствующих сущностей и `ErrInvalidTransition` для повторного завершения;
это позволит API следующего этапа выбирать корректный HTTP-ответ без разбора
текста ошибки.

## Критерий готовности

Код более высокого уровня может создать источник, начать и завершить запуск,
а затем получить актуальное состояние обоих объектов без прямого SQL.
