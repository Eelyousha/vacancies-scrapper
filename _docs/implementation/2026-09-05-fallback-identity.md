# Fallback-идентичность вакансий

**Дата:** 2026-09-05
**Статус:** выполнено
**Этап ТЗ:** [этапы 1 и 3](../05-implementation-plan.md)

## Проблема и цель

Некоторые сайты создают новую ссылку для одной вакансии при каждом запуске.
Идентичность только по каноническому URL в таком случае создаёт ложные новые
вакансии и делает будущую архивацию небезопасной.

Цель — реализовать YAML `identity.fallback_fields`: при его наличии набор
полей всегда становится ключом сопоставления вакансии вместо URL.

## Границы

Входит:

* валидация набора fallback-полей в YAML;
* миграция технического `identity_key` и сохранение канонического URL отдельно;
* сопоставление, дедупликация и ID вакансии по fallback-ключу;
* тесты динамического URL, повторов и ошибочного YAML.

Не входит:

* архивирование отсутствующих вакансий;
* fallback без хотя бы одного извлечённого значения;
* изменение состава fallback-полей без создания новой вакансии.

## План и решение

Пользователь подтвердил правило: заданный `identity.fallback_fields` всегда
заменяет URL как идентичность. Допустимы `title`, `company`, `salary` и
`description`; YAML валидирует непустой набор, известные значения и отсутствие
повторов. Поля и их значения однозначно сериализуются и хешируются. Изменение
состава полей либо их значения создаёт новую вакансию.

`canonical_link` остаётся нормализованным URL для перехода пользователя.
Отдельный `identity_key` мигрируется из существующего `canonical_link` и
получает уникальный индекс с `source_id`, поэтому прежние записи сохраняют
семантику URL-идентичности. Миграция пересоздаёт таблицу, убирая прежнюю
уникальность URL; на время этого SQLite foreign keys отключаются на единственном
соединении и после переноса проверяются через `foreign_key_check`.

## Проверка и результат

Проверены сценарии:

1. два разных URL с одинаковыми fallback-полями дают одну вакансию — пройден;
2. изменение fallback-поля создаёт новую вакансию — пройден;
3. без fallback сохраняется URL-идентичность — пройден существующими тестами;
4. пустой, повторяющийся, неизвестный и `link` в fallback отклоняются YAML-валидатором — пройден;
5. миграция заполняет `identity_key` существующих записей — пройден.

Выполнены `go test ./...`, `go vet ./...`, `go build ./...` и `git diff
--check` — успешно.

## Сверка с ТЗ и следующий шаг

Решение реализует ограничение из [модели данных](../02-data-model.md) и
разблокирует безопасную архивацию. Следующий шаг — архивировать только
невстреченные вакансии полного успешного запуска.
