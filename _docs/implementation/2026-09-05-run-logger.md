# Выделение журнала запусков

**Дата:** 2026-09-05
**Статус:** выполнено
**Этап ТЗ:** [этапы 2 и 3](../05-implementation-plan.md)

## Проблема и цель

В `internal/runner` смешаны регистрация источника и запись результатов
запуска: вакансий, статусов, счётчиков, ошибок и `meta_json`. Вторую
ответственность потребуется переиспользовать для API и будущих планировщиков.

Цель — выделить отдельный компонент журнала запусков с единым интерфейсом
успешного, частичного и ошибочного завершения.

## Границы

Входит:

* пакет `internal/runlog` для записи результатов и ошибок запуска;
* перевод CLI и тестов на новый компонент;
* сохранение существующих статусов, счётчиков и формата диагностик.

Не входит:

* структурированный лог stdout/stderr;
* изменение схемы SQLite или пользовательского поведения CLI;
* запуск по расписанию и API.

## План и решение

Добавлен `internal/runlog` с `Finish` и `Fail`. Он получает ID уже начатого
запуска, результат скрапера и сохраняет наблюдения вакансий, терминальный
статус, счётчики, ошибку и `meta_json`. `runner` теперь отвечает только за
создание/обновление источника и запись `running`; CLI использует оба компонента.
Это сохраняет формат SQLite и JSON без изменения параметров или stdout CLI.

## Проверка и результат

Проверены сценарии:

1. успех сохраняет вакансию, счётчики и `meta_json` — пройден;
2. ошибка детальной страницы становится `partial`/`incomplete` — пройден;
3. фатальная ошибка становится `failed`/`unknown` — пройден;
4. CLI сохраняет timeout-ошибку отдельным контекстом — пройден.

Выполнены `go test ./...`, `go vet ./...`, `go build ./...` и `git diff
--check` — успешно.

## Сверка с ТЗ и следующий шаг

Разделение сохраняет требования ТЗ к `scraping_runs` и `meta_json`, подготавливая
повторное использование для API и планировщика. Следующая функциональная задача
остаётся fallback-фингерпринтом.
