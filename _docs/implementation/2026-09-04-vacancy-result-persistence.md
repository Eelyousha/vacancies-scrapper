# Сохранение результатов вакансий

**Дата:** 2026-09-04  
**Статус:** выполнено  
**Этап ТЗ:** [этап 3 — дельта и архивирование](../05-implementation-plan.md#этап-3--дельта-и-архивирование)

## Проблема и цель

Источники и запуски уже сохраняются, но результат скрапера пока не попадает в
таблицу `vacancies`. Нельзя отличить новую вакансию от изменённой или показать
состав определённого запуска.

Цель — транзакционно применить наблюдения одного `running` запуска, вычислить
дельту и записать историю полей, определённых ТЗ.

## Границы

Входит:

* канонизация URL и стабильный SHA-256 идентификатор вакансии;
* создание вакансии, обновление и `unchanged`;
* история изменений `title`, `company`, `salary`, `link`;
* состав запуска с disposition для каждой увиденной вакансии.

Не входит:

* завершение запуска и обновление его итоговых счётчиков;
* архивация отсутствующих вакансий: она будет отдельной задачей и разрешена
  только после доказанно полного успешного запуска;
* fallback-фингерпринт без ссылки и подключение к Chromium CLI.

## План и решение

Метод хранилища получает `run_id` и наблюдаемые вакансии. Он проверяет, что
запуск находится в `running`, и в одной транзакции обрабатывает все наблюдения.
Канонический URL удаляет фрагмент, приводит схему и хост к нижнему регистру,
сортирует query-параметры и отбрасывает `utm_*`, `gclid`, `fbclid`.

## Проверка и результат

Тесты выполняются на временной SQLite-БД:

1. первая встреча вакансии создаёт запись с disposition `added` — пройден;
2. неизменная повторная встреча даёт `unchanged` — пройден;
3. изменение зарплаты обновляет вакансию, создаёт историю и `updated` — пройден;
4. tracking-параметры и фрагмент не создают дубликат — пройден;
5. нельзя применить результаты к завершённому запуску — пройден.

В ходе проверки обнаружено и исправлено два дефекта нормализации URL: удаление
ключей query во время обхода map могло пропустить tracking-параметр, а
`url.ParseRequestURI` считывал `#fragment` как часть query. Канонизация теперь
собирает ключи перед удалением и использует `url.Parse` с явной проверкой
абсолютного URL.

Выполнены `go test ./...`, `go vet ./...`, `go build ./...` и `git diff
--check` — все проверки успешны.

## Сверка с ТЗ и следующий шаг

Результат соответствует транзакционному обновлению вакансий, истории полей и
составу запуска из этапа 3. Архивация намеренно не реализована: ТЗ разрешает её
только при `status=success` и `completion_status=complete`.

Правило идентичности уточнено отдельной
[записью](2026-09-04-url-identity-rule.md): изменение канонического URL создаёт
новую вакансию. Для источников, у которых URL нестабилен, следующим шагом
реализуется YAML fallback-фингерпринт; безопасная архивация следует после него.
