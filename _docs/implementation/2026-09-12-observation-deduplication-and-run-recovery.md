# Дедупликация наблюдений и восстановление прерванного запуска

**Дата:** 2026-09-12
**Статус:** выполнено
**Этап ТЗ:** [этапы 2, 3 и 5](../05-implementation-plan.md)

## Проблема и цель

Один сайт может показать одну вакансию в нескольких карточках. Сейчас два
наблюдения с одинаковой канонической identity откатывают всю транзакцию и
завершают run с ошибкой. Если процесс сервера был остановлен в момент запуска,
состояние `running` сохраняется в SQLite и запрещает следующие ручные запуски.

Цель — считать повтор одной identity внутри одного ответа сайта одной
вакансией, а незавершённые после перезапуска сервера runs явно завершать как
ошибочные, не ослабляя блокировку реально параллельных запусков. Каждая ошибка
ручного lifecycle должна фиксироваться в source/run и в локальном журнале.

## Границы

Входит: дедупликация наблюдений по уже определённой identity с детерминированным
сохранением первой карточки; восстановление `running` runs при открытии БД;
диагностика в run и source; структурированные записи в журнал сервера о начале
и завершении ручного запуска; unit-тесты.

Не входит: параллельный сбор, очередь фоновых jobs, ручная отмена запуска,
слияние конфликтующих данных из повторных карточек и изменение identity между
запусками.

## План и решение

Тесты зафиксировали: две карточки с равной identity создают одну
вакансию и один элемент состава запуска; незавершённый run после повторного
запуска сервера становится `failed`, а источник снова доступен для нового
запуска; ошибка завершения lifecycle не остаётся незамеченной. Действующий
`running` в том же процессе по-прежнему возвращает `ErrInvalidTransition`.

В хранилище повторная identity в одной порции наблюдений пропускается: первая
карточка в порядке документа сохраняется детерминированно. `vacancy` и строка
состава run остаются единственными, а счётчики учитывают одну вакансию.

`RecoverInterruptedRuns` вызывается перед началом приёма запросов HTTP-сервером,
а не из общего `storage.Open`: так отдельный процесс не может ошибочно
завершить живой server-side запуск. Все оставшиеся после остановки процесса
`running` run и source получают `failed` и текст причины.

HTTP lifecycle пишет в стандартный журнал начало, отказ блокировки, успешный
итог и ошибку каждого ручного запуска. Флаг `-log-file` дублирует эти записи
в указанный файл в режиме append, сохраняя stderr. Ошибка `Finish` обязательно
пытается завершить run через `Fail`; ошибка этой второй операции возвращается
вместе с исходной и попадает в журнал.

## Проверка и результат

Пройдены unit-сценарии URL- и fallback-дубликатов, восстановления прерванного
run и сохранения блокировки живого запуска. Также проверен существующий сценарий
timeout: run и source фиксируются как `failed`. Выполнены: `go test ./...`,
`go vet ./...`, `go build ./...`, `git diff --check`.
