# Начальная SQLite-схема

**Дата:** 2026-09-01  
**Статус:** выполнено  
**Этап ТЗ:** [этап 0 — фундамент](../05-implementation-plan.md#этап-0--фундамент)

## Проблема и цель

До этого инкремента проект мог извлекать вакансии только в JSON стандартного
вывода. Не было постоянного хранилища, поэтому нельзя было запоминать источники,
результаты запусков и последующие изменения вакансий.

Цель — заложить безопасную и воспроизводимую SQLite-инфраструктуру, на которую
можно поэтапно добавлять репозитории и бизнес-логику.

## Границы

Выполнено:

* открытие локального SQLite-файла;
* включение внешних ключей;
* версионируемые миграции, применяемые транзакционно;
* начальная схема и её индексы из модели данных;
* автоматические проверки миграций и внешних ключей.

Не входит в этот инкремент:

* создание, чтение и обновление источников через репозитории;
* запись результата скрапера, дедупликация и архивирование;
* HTTP API, UI, расписания и создание файла БД из CLI.

## Решение

Выбран `modernc.org/sqlite` — SQLite-драйвер на Go без требования CGO. Это
позволяет собирать приложение обычной Go-сборкой и не добавляет системную
зависимость от компилятора C.

Пакет `internal/storage` открывает конкретный файл БД. При каждом открытии он:

1. передаёт драйверу настройку `foreign_keys(1)`;
2. дополнительно выполняет `PRAGMA foreign_keys = ON`, чтобы ошибка настройки
   проявилась при открытии, а не во время записи;
3. создаёт служебную таблицу `schema_migrations`, если её ещё нет;
4. применяет только отсутствующие миграции в порядке их версии.

Каждая миграция и отметка о её применении находятся в одной транзакции. Если
SQL миграции завершится ошибкой, версия не будет записана, а неполное изменение
схемы откатится.

## Состав схемы

Начальная миграция создаёт следующие сущности.

| Таблица | Назначение |
|---|---|
| `sources` | Конфигурация сайта, расписание и последнее состояние источника. |
| `scraping_runs` | Один запуск сбора, его длительность, статус, счётчики и диагностика. |
| `vacancies` | Текущее состояние вакансии, её ссылка и пользовательский статус. |
| `vacancy_history` | Изменения отслеживаемых полей вакансии. |
| `scraping_run_vacancies` | Состав конкретного запуска и результат для каждой вакансии. |
| `schema_migrations` | Версии уже применённых миграций. |

На уровне БД добавлены проверки допустимых статусов, уникальность `slug`
источника и пары «источник + каноническая ссылка», а также внешние ключи между
всеми зависимыми сущностями. Индексы покрывают выборки из ТЗ: вакансии по
источнику и статусу, последний запуск вакансии, запуски источника по времени и
состав запуска.

## Проверка

Тесты выполняются на временном SQLite-файле и не требуют Chromium или внешнего
сайта.

| Сценарий | Ожидаемый результат | Результат |
|---|---|---|
| Открытие чистого файла | Созданы все таблицы, записана миграция версии 1. | Пройден |
| Повторное открытие файла | Миграция не применяется повторно. | Пройден |
| Вакансия с отсутствующим `source_id` | SQLite отклоняет запись по внешнему ключу. | Пройден |

После изменения выполнены `go test ./...`, `go vet ./...`, `go build ./...` и
`git diff --check` — все проверки успешны.

## Следующий шаг

Добавить репозитории для `sources` и `scraping_runs`, покрыв их тестами. После
этого можно подключать текущий скрапер к транзакционному сохранению запусков и
реализовывать дельту вакансий отдельным инкрементом.
