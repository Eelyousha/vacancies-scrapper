# Модуль планирования повторных обходов

**Дата:** 2026-09-12
**Статус:** выполнено
**Этап ТЗ:** [этапы 2, 3 и 5](../05-implementation-plan.md)

## Проблема и цель

Повторный ограниченный обход всегда начинает динамическую ленту с начала и
видит уже известные вакансии. Простой курсор не решает проблему источника с
произвольной сортировкой: новая карточка может появиться в середине.

Цель — выделить выбор стратегии повторного обхода в независимый модуль и
реализовать безопасную первую стратегию: короткие head-проходы для быстрого
поиска новых вакансий и периодические полные reconciliation-проходы для
покрытия всей доступной выдачи.

## Границы

Входит: `internal/revisit` с детерминированным планом; head-лимит и период
reconciliation с безопасными defaults; интеграция в ручной lifecycle;
неполный статус head-run, исключающий архивацию; тесты.

Не входит: хранение site-specific cursor/offset, URL-шаблоны страниц, фоновые
расписания, параллельный сбор и редактирование политики в HTML.

## План и решение

Тесты зафиксировали: первые несколько terminal non-failed запусков ограничены
head-окном; каждый N-й запуск получает полный лимит из YAML; при отсутствии
пагинации план всегда полный; partial head-run не архивирует вакансии.

Начальная политика не меняет YAML: head ограничен тремя итерациями, полный
reconciliation выполняется каждым пятым terminal non-failed ручным запуском.
Число попыток со статусом `success` или `partial` берётся из журнала источника;
`failed` и `running` не сдвигают цикл. Модуль `internal/revisit` возвращает
отдельный план с лимитом и completion status; lifecycle применяет лимит к копии
конфига и передаёт status в runlog. Поэтому стратегию cursor/offset можно будет
добавить без переписывания lifecycle.

## Проверка и результат

Пройдены unit-тесты planner и интеграционный сценарий lifecycle: три head-run
не архивируют вакансию за пределами окна; последующий full-run применяет
исходный лимит и архивирует действительно неувиденную вакансию. Выполнены:
`go test ./...`, `go vet ./...`, `go build ./...`, `git diff --check`.

## Сверка с ТЗ и следующий шаг

Развивает этапы 2–3 и создаёт расширяемую основу этапа 5. Site-specific
cursor/offset пока не реализован; на динамических лентах полное покрытие даёт
каждый пятый проход. Связанная карточка [№ 26](../backlog.md) выполнена.
Следующий возможный шаг — декларативные cursor/offset для сайтов с устойчивой
URL-пагинацией.
