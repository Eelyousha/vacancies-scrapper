# Подключение CLI к SQLite

**Дата:** 2026-09-05
**Статус:** выполнено
**Этап ТЗ:** [этапы 0, 2 и 3](../05-implementation-plan.md)

## Проблема и цель

CLI извлекает вакансии и печатает JSON, но не использует уже готовые
репозитории SQLite. Поэтому данные запуска, YAML-конфигурация, дельта вакансий
и диагностика теряются после завершения процесса.

Цель — сделать штатный запуск CLI транзакционно сохраняемым: зарегистрировать
или обновить источник, создать и завершить запуск, применить вакансии и
сохранить диагностику в соответствии с моделью данных.

## Границы

Входит:

* флаг пути SQLite-БД и её открытие с миграциями;
* создание либо обновление ручного источника, запуск и его терминальный статус;
* сохранение вакансий, дельты, счётчиков и JSON-диагностики результата;
* тесты успешного, частичного и ошибочного жизненного цикла.

Не входит:

* архивирование отсутствующих вакансий;
* fallback-фингерпринт и dry run/test token;
* ручной выбор стабильного идентификатора источника в CLI.

## План и решение

Временно источником CLI управляет `site_name`: из него формируется
детерминированный читаемый slug с хеш-суффиксом. Повторный запуск с тем же
названием обновляет YAML источника; пользователь подтвердил, что смена
`site_name` пока допустимо создаёт отдельный источник.

Добавлен `internal/runner`, который до открытия Chromium создаёт или обновляет
ручной источник и записывает `running`-запуск. После сбора он вносит вакансии
транзакционным репозиторием, сохраняет дельту и завершает запуск. Успешный
полный результат имеет `success`/`complete`; ошибки детальных страниц либо
диагностические лимиты — `partial`/`incomplete`; ошибка скрапера —
`failed`/`unknown`. Метаданные страницы, пагинации и ошибок деталей попадают в
`meta_json`; текст фатальной ошибки также сохраняется.

CLI получил `-database` (по умолчанию `vacancies.db`). Для ошибки Chromium
используется отдельный короткий контекст SQLite: отмена `run-timeout` не
оставляет запуск в состоянии `running`.

## Проверка и результат

Проверены сценарии:

1. новый YAML-источник создаётся, вакансия, успешный запуск и диагностический
   JSON сохранены — пройден;
2. повторный запуск того же `site_name` обновляет YAML существующего источника
   — пройден;
3. ошибка детальной страницы даёт `partial`/`incomplete` — пройден;
4. ошибка скрапера завершает уже начатый запуск как `failed`/`unknown` —
   пройден;
5. отменённый контекст скрапера не препятствует сохранению failed-запуска —
   пройден.

Выполнены `go test ./...`, `go vet ./...`, `go build ./...` и `git diff
--check` — успешно.

## Сверка с ТЗ и следующий шаг

Инкремент соединяет алгоритм запуска из раздела 03 с `sources`,
`scraping_runs`, `vacancies`, историей и составом запуска из раздела 02.
Архивация намеренно не вызывается: она остаётся разрешённой только после
доказанно полного успешного запуска. Следующий шаг — fallback-фингерпринт,
затем безопасная архивация.
